# Аутентификация и авторизация в этом проекте

Этот файл — учебный разбор того, как в проекте устроена регистрация, вход и
проверка личности пользователя между двумя независимыми сервисами
(`user-service` и `task-service`). Он объясняет и общую механику (как это
делают в индустрии), и то, что конкретно реализовано в коде, с указанием
файлов и строк.

## 1. Регистрация

`services/user-service/app/routers/auth.py`, `POST /auth/register`.

Пароль **никогда** не хранится в открытом виде. При регистрации он проходит
через bcrypt (`services/user-service/app/security.py`, `hash_password`):

```python
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)
```

bcrypt — это не просто хэш-функция вроде SHA-256, а специально медленная
функция с встроенной солью (случайное значение, уникальное для каждого
пароля). Это защищает от:

- **Rainbow table атак** — заранее посчитанных таблиц "хэш -> пароль" (соль
  делает такую таблицу бесполезной, т.к. у каждого пользователя разный хэш
  даже при одинаковом пароле).
- **Brute-force / offline перебора** — bcrypt намеренно медленный (можно
  настраивать "cost factor"), поэтому перебор миллиардов паролей в секунду,
  как для SHA-256, тут не работает.

В базе (`models.py`, поле `hashed_password`) лежит только результат
`hash_password`, восстановить из него исходный пароль математически
нельзя — можно только заново хэшировать введённый пароль и сравнить хэши
(`verify_password`).

Отдельный эндпоинт `POST /auth/admin/register` защищён общим секретом
`X-Admin-Secret` (сверяется с `ADMIN_BOOTSTRAP_SECRET` из `.env`) — это
просто механизм "бутстрапа" первого админа в учебном проекте, к JWT
отношения не имеет.

## 2. Вход (login) и что такое JWT

`POST /auth/login` проверяет пароль (`verify_password`) и, если всё
совпало, выдаёт пару токенов (`security.py`, `_create_token`):

```python
def _create_token(user_id, role, token_type, expires_delta):
    payload = {
        "sub": str(user_id),   # кто это
        "role": role,           # какая у него роль
        "type": token_type,     # "access" или "refresh"
        "iat": now,              # когда выпущен
        "exp": now + expires_delta,  # когда истекает
        "iss": settings.jwt_issuer,  # кто выпустил
    }
    return jwt.encode(payload, settings.jwt_secret_key, algorithm="HS256")
```

JWT (JSON Web Token) — это не "ключ доступа" в смысле пароля, а
**подписанный набор данных**. Токен состоит из трёх частей,
разделённых точками: `header.payload.signature`. Header и payload — это
просто base64 от JSON (их может прочитать кто угодно, они не зашифрованы!),
а signature — криптографическая подпись первых двух частей. Смысл JWT не
в секретности содержимого, а в том, что **никто не может подделать или
изменить payload** без знания секретного ключа — при малейшем изменении
данных подпись перестанет сходиться.

Из этого следует важный вывод: **не кладите в JWT ничего секретного**
(пароли, номера карт и т.д.) — там достаточно положить публично неопасные
данные вроде `sub` (id пользователя) и `role`.

У нас две токена:
- **access_token** — живёт 15 минут (`ACCESS_TOKEN_EXPIRE_MINUTES`),
  именно им авторизуются запросы к API.
- **refresh_token** — живёт 7 дней (`REFRESH_TOKEN_EXPIRE_MINUTES=10080`
  минут), предназначен для получения нового access-токена без повторного
  ввода пароля.

`POST /auth/refresh` принимает `refresh_token` и выдаёт новый
`access_token` (без похода в БД — так же, как проверка access-токена в
task-service): проверяется подпись, `exp`, `iss` и `type == "refresh"`, и
если всё сошлось, выпускается новый access-токен с тем же `sub`/`role`.
Сам refresh_token при этом не ротируется и не отзывается — отзыв
(blocklist/whitelist в БД или Redis) в этой итерации не реализован.

Короткий TTL access-токена — это компромисс: если токен утечёт (например,
через XSS на фронтенде), у атакующего будет всего 15 минут, а не 7 дней,
чтобы им воспользоваться.

## 3. Как Task-service доверяет токену, который выпустил User-service

Это ключевой вопрос микросервисной аутентификации: два независимых
процесса, у каждого своя база данных, но Task-service должен как-то
проверять, что токен настоящий, не спрашивая пароль заново и не заходя в
БД User-service на каждый запрос.

### Вариант A — общий секрет, HS256 (то, что реализовано в проекте)

Оба сервиса читают одну и ту же переменную окружения `JWT_SECRET_KEY` из
общего `.env` (см. `docker-compose.yml`, `env_file: .env` у обоих
сервисов).

- User-service подписывает токен: `jwt.encode(payload, JWT_SECRET_KEY,
  algorithm="HS256")` (`user-service/app/security.py`).
- Task-service проверяет тем же секретом: `jwt.decode(token,
  JWT_SECRET_KEY, algorithms=["HS256"], issuer=...)`
  (`task-service/app/auth.py`, `get_current_user`).

Алгоритм HS256 — это HMAC-SHA256, симметричная схема: **один и тот же ключ
используется и для подписи, и для проверки**. Если у сервиса есть ключ для
проверки — у него автоматически есть всё необходимое, чтобы подписать
(подделать) новый токен.

Проверка происходит полностью локально: Task-service ни разу не ходит в
User-service, чтобы проверить токен — только сравнивает подпись с уже
известным ему секретом. Это быстро (никакого сетевого вызова на каждый
запрос) и просто в реализации.

**Плата за простоту** — модель доверия: оба сервиса имеют равные права.
Если бы Task-service скомпрометировали, атакующий получил бы секрет и мог
бы выписать токен с `role: "admin"` и любым `sub`, то есть притвориться
кем угодно перед User-service тоже. В учебном/пет-проекте, где оба
сервиса пишет и деплоит один и тот же человек/команда, это приемлемый
компромисс ради простоты.

### Вариант B — асимметричная подпись, RS256 + JWKS (чем это отличается)

Раньше в этом проекте было реализовано именно так, и вот в чём была
разница:

- User-service хранит **приватный** RSA-ключ у себя и им подписывает
  токены.
- **Публичный** ключ отдаётся всем желающим по HTTP-эндпоинту вида
  `/.well-known/jwks.json` (JWKS — JSON Web Key Set).
- Task-service при старте один раз скачивает публичный ключ, кэширует его
  в памяти и дальше проверяет подписи им же, тоже без сетевых вызовов на
  каждый запрос.

Разница с HS256 принципиальная: публичным ключом можно **только
проверять** подпись, подписать им новый токен нельзя. Значит, даже если
скомпрометируют Task-service (или любой другой сервис-потребитель), у
атакующего максимум окажется публичный ключ — им нельзя выписать ни один
новый валидный токен. Приватный ключ, который единственный умеет
подписывать, никогда не покидает User-service.

Это стандарт, на котором строятся Auth0, Keycloak, AWS Cognito, Okta и
протокол OAuth2/OIDC в целом: сервер авторизации подписывает приватным
ключом, ресурс-серверы проверяют публичным через JWKS.

### Почему в этом проекте выбрали HS256, а не RS256

Проект учебный: два сервиса, один владелец, задача — понять, как работает
JWT и разделение "выпуск / проверка токена" между сервисами, а не строить
production-grade систему с множеством независимых команд и произвольным
количеством ресурс-серверов. HS256:

- Не требует генерации, хранения и ротации RSA-ключей.
- Не требует отдельного публичного эндпоинта и логики его выкачивания при
  старте (`load_public_key`, ретраи, кэш в памяти).
- Сводится к одной строке в `.env`, разделяемой между сервисами через
  `docker-compose.yml`.

Цена этой простоты — то самое совмещение прав "подписывать" и
"проверять" в одном ключе, описанное выше. В реальной проде, где
сервисов-потребителей токена много и ими управляют разные команды, это
обычно перевешивает выгоду от простоты, и выбирают RS256/JWKS. Для
учебного двух-сервисного проекта — наоборот.

### Важное уточнение: ключ один на весь сервис, не на пользователя

Секрет (`JWT_SECRET_KEY`) — это единственная строка, общая для **всех**
пользователей и **всех** токенов, которые вообще когда-либо выпустит
User-service. Он не хранится "по одному на пользователя" и не растёт со
временем — это не пароль конкретного юзера, а ключ всего сервиса-эмитента.
`sub` (id пользователя) внутри токена — это просто поле данных, а не
отдельный криптографический ключ.

## 4. Проверка токена на каждый запрос

`services/task-service/app/auth.py`:

```python
async def get_current_user(credentials: HTTPAuthorizationCredentials = Depends(bearer_scheme)) -> CurrentUser:
    try:
        payload = jwt.decode(
            credentials.credentials, settings.jwt_secret_key, algorithms=["HS256"], issuer=settings.jwt_issuer
        )
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
    if payload.get("type") != "access":
        raise HTTPException(status_code=401, detail="Invalid token type")
    return CurrentUser(id=uuid.UUID(payload["sub"]), role=payload["role"])
```

Клиент передаёт токен в заголовке `Authorization: Bearer <access_token>`
(FastAPI берёт его через `HTTPBearer`). Проверяется:
- подпись (совпадает ли HMAC с тем, что ожидается по секрету);
- `exp` — не истёк ли токен (библиотека `pyjwt` делает это автоматически);
- `iss` — что токен выпущен именно `user-service`;
- `type == "access"` — чтобы нельзя было использовать refresh-токен вместо
  access-токена для доступа к API.

`require_admin` — дополнительная проверка `role == "admin"` поверх
`get_current_user`, используется в эндпоинтах вроде создания задачи или
`approve`/`reject`.

## 5. Что делает фронтенд с токеном (в проекте фронта нет, но вот теория)

Ответ `/auth/login` — обычный JSON:
`{"access_token": "...", "refresh_token": "...", "token_type": "bearer"}`.
Браузер **не** сохраняет его автоматически — это просто данные в теле
HTTP-ответа. Что с ними делать дальше, решает JS-код фронтенда. На практике
встречаются варианты:

| Способ | Где хранится | Плюсы | Минусы |
|---|---|---|---|
| `localStorage` | В браузере, доступно JS, переживает перезагрузку | Просто в реализации | Любая XSS-уязвимость на странице ворует токен |
| In-memory (переменная/state) | Только в оперативной памяти вкладки | XSS не может просто прочитать storage | Токен теряется при F5, нужен silent-refresh при загрузке |
| `httpOnly` cookie | Cookie, которую ставит сервер (`Set-Cookie`), JS её не видит | Недоступна для чтения через XSS | Нужна защита от CSRF (`SameSite`, CSRF-токен) |

Частая практика в проде — гибрид: access-токен держат в памяти (или
короткоживущей cookie), а refresh-токен — в `httpOnly` + `Secure` +
`SameSite` cookie, которую браузер сам подставляет в запросы, а JS
никогда не видит. Это одновременно снижает риск и XSS, и CSRF.

Наш API токены в cookie не кладёт (`Set-Cookie` нигде не выставляется) —
он просто возвращает их в JSON, а выбор способа хранения остаётся за тем
фронтендом, который когда-нибудь будет подключён к этому API.

## 6. Итоговый путь пользователя

1. `POST /auth/register` (user-service) → пароль хэшируется bcrypt,
   создаётся пользователь с ролью `performer`.
2. `POST /auth/login` (user-service) → пароль сверяется с хэшем, в ответ
   выдаётся `access_token` + `refresh_token`, подписанные `JWT_SECRET_KEY`
   алгоритмом HS256.
3. Клиент кладёт `access_token` в заголовок `Authorization: Bearer ...`
   каждого запроса к task-service (`POST /tasks`, `/claim`, `/complete`
   и т.д.).
4. Task-service проверяет подпись **локально**, тем же `JWT_SECRET_KEY`,
   без единого обращения к user-service — доверие между сервисами держится
   исключительно на общем секрете.
